# Requirements Document

## Introduction

The BLUETEETH Patient Management Portal is a comprehensive, cloud-based medical CRM and Electronic Medical Records (EMR) system built for BLUETEETH Dental Care. The portal enables clinic staff and administrators to capture, manage, and retrieve patient records across four distinct visit types: website leads, free dental camps, clinic visits, and home visits. It provides doctor management, file/report storage, analytics dashboards, and role-based access control — all backed by Firebase cloud infrastructure and delivered through a modern React/Next.js frontend.

---

## Glossary

- **Portal**: The BLUETEETH Patient Management Portal web application.
- **Admin**: An authenticated user with the `super_admin` role who has full read, write, and delete permissions.
- **Receptionist**: An authenticated user with the `receptionist` role who can add and edit patients but cannot delete records.
- **Doctor**: An authenticated user with the `doctor` role who can view and update treatment records for their assigned patients.
- **Patient**: A person whose dental care record is stored in the Portal.
- **Patient_Record**: A Firestore document in the `patients` collection containing all demographic, medical, and visit data for a Patient.
- **Visit_Type**: The classification of how a Patient engaged with BLUETEETH — one of: `Website Lead`, `Free Camp`, `Clinic Visit`, or `Home Visit`.
- **Auth_Service**: Firebase Authentication, responsible for identity verification and session management.
- **Firestore**: Firebase Cloud Firestore, the NoSQL database storing all Portal data.
- **Storage**: Firebase Cloud Storage, used for file uploads (reports, X-rays, prescriptions, images).
- **Patient_ID**: A system-generated unique identifier assigned to each Patient_Record at creation time.
- **Report**: A file (PDF, JPG, PNG, or DOCX) uploaded to Storage and linked to a Patient_Record.
- **Prescription**: A PDF document generated by the Portal summarising a Patient's treatment and medicines.
- **Dashboard**: The main landing page after login, displaying summary cards and charts.
- **Sidebar**: The persistent left-hand navigation panel visible on all authenticated pages.
- **Search_Service**: The Portal module responsible for querying patients by name, mobile, doctor, disease, date, or Visit_Type.
- **Analytics_Module**: The Portal module that aggregates and visualises patient, revenue, and visit data.
- **Camp_Management**: The sub-module for organising and recording free dental camp events and their associated patients.
- **Activity_Log**: An append-only Firestore collection recording all create, update, and delete actions with actor identity and timestamp.

## Requirements

---

### Requirement 1: Authentication and Session Management

**User Story:** As an Admin, I want to log in with my email and password and have my session persist across page refreshes, so that I do not need to re-authenticate every time I open the Portal.

#### Acceptance Criteria

1. THE Auth_Service SHALL authenticate users using email and password credentials via Firebase Authentication.
2. WHEN a user submits valid credentials, THE Portal SHALL redirect the user to the Dashboard within 3 seconds.
3. WHEN a user submits invalid credentials, THE Portal SHALL display a descriptive error message without revealing whether the email or password was incorrect.
4. WHILE a user is authenticated, THE Portal SHALL persist the Firebase session across browser refreshes and tab reopens.
5. WHEN an unauthenticated user navigates to any protected route, THE Portal SHALL redirect the user to the Login page.
6. WHEN a user clicks Logout, THE Auth_Service SHALL invalidate the session and THE Portal SHALL redirect the user to the Login page within 1 second.
7. WHEN a user requests a password reset, THE Auth_Service SHALL send a password-reset email to the registered address within 60 seconds.
8. WHILE authentication state is being resolved on page load, THE Portal SHALL display a loading screen to prevent a flash of unauthenticated content.
9. THE Portal SHALL enforce role-based route protection so that a Doctor role cannot access Admin-only pages and a Receptionist role cannot access delete operations.

---

### Requirement 2: Dashboard Overview

**User Story:** As an Admin, I want a dashboard that shows key clinic metrics at a glance, so that I can monitor the clinic's performance without running manual reports.

#### Acceptance Criteria

1. WHEN an authenticated user opens the Dashboard, THE Dashboard SHALL display summary cards for: Total Patients, Today's Patients, Total Revenue, Reports Uploaded, Free Camp Patients, Website Leads, and Active Doctors.
2. THE Dashboard SHALL display a Monthly Patients Chart showing patient registration counts grouped by month for the current calendar year.
3. THE Dashboard SHALL display a Revenue Graph showing total treatment charges grouped by month for the current calendar year.
4. THE Dashboard SHALL display a Visit Analytics chart breaking down patient counts by Visit_Type for the current calendar year.
5. WHEN new Patient_Records are created or updated, THE Dashboard SHALL reflect updated metric values within 30 seconds without requiring a full page reload.
6. THE Dashboard SHALL display the current date in the top navigation bar.
7. THE Dashboard SHALL display a notification icon in the top navigation bar that shows a badge count of unread system notifications.

---

### Requirement 3: Patient Record Creation

**User Story:** As a Receptionist or Admin, I want to add a new patient record with full demographic and medical details, so that the clinic has a complete, searchable record for every patient.

#### Acceptance Criteria

1. WHEN a user submits the Add Patient form with all required fields, THE Portal SHALL create a Patient_Record in Firestore and assign a unique Patient_ID within 5 seconds.
2. THE Portal SHALL auto-generate the Patient_ID using a sequential or UUID-based scheme so that no two Patient_Records share the same Patient_ID.
3. THE Portal SHALL capture the following demographic fields for every Patient_Record: Patient Name, Age, Gender, Mobile Number, Alternate Number, Address, City, State, and Pincode.
4. THE Portal SHALL capture the following medical fields for every Patient_Record: Disease, Symptoms, Treatment, Medicines, Treatment Charge, Doctor Name, Visit_Type, Follow-Up Date, and Notes.
5. WHEN a user selects a Visit_Type, THE Portal SHALL restrict the value to one of: `Website Lead`, `Free Camp`, `Clinic Visit`, or `Home Visit`.
6. IF a user submits the Add Patient form with any required field empty, THEN THE Portal SHALL display a field-level validation error and SHALL NOT create a Patient_Record.
7. WHEN a Patient_Record is created, THE Portal SHALL record the `createdAt` timestamp and the identity of the creating user in the Patient_Record.
8. THE Portal SHALL generate a QR code encoding the Patient_ID for each Patient_Record, available for display and printing on the patient detail page.

---

### Requirement 4: Patient Record Update and Deletion

**User Story:** As a Doctor or Admin, I want to edit and update a patient's treatment details after each visit, so that the record always reflects the latest clinical information.

#### Acceptance Criteria

1. WHEN an authorised user submits an edited Patient_Record, THE Portal SHALL update the corresponding Firestore document and record the `updatedAt` timestamp within 5 seconds.
2. WHEN a Patient_Record is updated, THE Portal SHALL preserve the original `createdAt` timestamp and Patient_ID without modification.
3. WHEN an Admin deletes a Patient_Record, THE Portal SHALL remove the document from Firestore and all associated files from Storage within 10 seconds.
4. IF a Receptionist or Doctor role attempts to delete a Patient_Record, THEN THE Portal SHALL deny the operation and display a permission error message.
5. WHEN a Patient_Record is deleted, THE Portal SHALL append an entry to the Activity_Log recording the deleted Patient_ID, the actor's identity, and the deletion timestamp.
6. THE Portal SHALL display a confirmation dialog before executing any delete operation, requiring explicit user confirmation.

---

### Requirement 5: Patient Listing and Table View

**User Story:** As an Admin, I want to view all patients in a sortable, filterable table, so that I can quickly find and manage any patient record.

#### Acceptance Criteria

1. THE Portal SHALL display all Patient_Records in a paginated table with the following columns: Patient_ID, Name, Mobile, Disease, Doctor, Treatment Charge, Visit_Type, Date, Status, and Report.
2. THE Portal SHALL provide per-row action buttons for: View, Edit, Delete, Download Report, and Print Prescription.
3. THE Portal SHALL support sorting the patient table by any column in ascending or descending order.
4. THE Portal SHALL support filtering the patient table by Visit_Type, Doctor Name, and date range simultaneously.
5. THE Portal SHALL paginate the patient table with a configurable page size of 10, 25, or 50 records per page.
6. THE Portal SHALL provide an Export CSV function that downloads all currently filtered Patient_Records as a CSV file.
7. THE Portal SHALL provide an Export PDF function that downloads all currently filtered Patient_Records as a formatted PDF file.
8. WHEN the patient table is loaded, THE Portal SHALL display results within 3 seconds for datasets up to 10,000 records.

---

### Requirement 6: Patient Search

**User Story:** As an Admin or Receptionist, I want to search for patients by multiple criteria, so that I can retrieve any patient record instantly without scrolling through the full list.

#### Acceptance Criteria

1. THE Search_Service SHALL support searching Patient_Records by: Patient Name, Mobile Number, Doctor Name, Disease, Visit Date, and Visit_Type.
2. WHEN a user enters a search query of 2 or more characters, THE Search_Service SHALL return matching results within 2 seconds.
3. THE Search_Service SHALL perform case-insensitive matching on text fields.
4. WHEN a search query returns no results, THE Portal SHALL display a "No patients found" message and SHALL NOT display an empty table.
5. THE Portal SHALL provide a global search bar in the top navigation bar accessible from all authenticated pages.
6. WHEN a user clears the search query, THE Portal SHALL restore the full unfiltered patient list.

---

### Requirement 7: Visit-Type Segmented Views

**User Story:** As an Admin, I want dedicated views for each patient visit type, so that I can manage website leads, free camp patients, clinic visits, and home visits independently.

#### Acceptance Criteria

1. THE Sidebar SHALL provide separate navigation links for: All Patients, Free Camp Patients, Website Patients, Clinic Visit Patients, and Home Visit Patients.
2. WHEN a user navigates to a visit-type page, THE Portal SHALL display only Patient_Records whose Visit_Type matches the selected category.
3. THE Portal SHALL apply all table features (search, sort, filter, pagination, export) independently within each visit-type view.
4. WHEN a Free Camp Patient_Record is created, THE Portal SHALL associate the record with a Camp_Management event if one is active.

---

### Requirement 8: Report and File Management

**User Story:** As a Doctor or Admin, I want to upload and manage patient reports, X-rays, and prescriptions, so that all clinical documents are stored securely and accessible from the patient record.

#### Acceptance Criteria

1. THE Portal SHALL accept file uploads in the following formats: PDF, JPG, PNG, and DOCX.
2. IF a user attempts to upload a file exceeding 10 MB, THEN THE Portal SHALL reject the upload and display a file-size error message.
3. IF a user attempts to upload a file in an unsupported format, THEN THE Portal SHALL reject the upload and display a format error message.
4. THE Portal SHALL support drag-and-drop file upload in addition to the standard file picker.
5. WHEN a file is successfully uploaded, THE Portal SHALL store the file in Firebase Storage and record the download URL in the associated Patient_Record within 10 seconds.
6. THE Portal SHALL display a preview of uploaded JPG and PNG files and a download link for PDF and DOCX files within the patient detail view.
7. WHEN an authorised user deletes a Report, THE Portal SHALL remove the file from Storage and clear the URL from the Patient_Record within 10 seconds.
8. THE Portal SHALL display the file name, upload date, and file size for each uploaded Report in the patient detail view.

---

### Requirement 9: Prescription and Invoice Generation

**User Story:** As a Doctor or Admin, I want to generate a printable PDF prescription and invoice for a patient, so that the patient receives a professional clinical document at the end of their visit.

#### Acceptance Criteria

1. WHEN a user clicks "Generate Prescription" on a Patient_Record, THE Portal SHALL produce a PDF document containing: Patient Name, Patient_ID, Doctor Name, Disease, Symptoms, Treatment, Medicines, Follow-Up Date, and clinic branding within 5 seconds.
2. WHEN a user clicks "Generate Invoice", THE Portal SHALL produce a PDF document containing: Patient Name, Patient_ID, Treatment Charge, treatment summary, date, and clinic branding within 5 seconds.
3. THE Portal SHALL allow the user to download the generated PDF or print it directly from the browser.
4. THE Portal SHALL store the generated prescription PDF URL in the Patient_Record's `prescriptionURL` field after generation.

---

### Requirement 10: Doctor Management

**User Story:** As an Admin, I want to add, edit, and manage doctor profiles, so that patient records can be accurately attributed to the correct treating doctor.

#### Acceptance Criteria

1. THE Portal SHALL capture the following fields for each Doctor profile: Doctor Name, Specialization, Mobile Number, Qualification, Experience (years), Availability schedule, and Profile Image.
2. WHEN an Admin creates a Doctor profile, THE Portal SHALL store the record in the `doctors` Firestore collection with a `createdAt` timestamp.
3. WHEN an Admin updates a Doctor profile, THE Portal SHALL update the Firestore document within 5 seconds.
4. WHEN an Admin deletes a Doctor profile, THE Portal SHALL remove the record from the `doctors` collection and display a confirmation dialog before executing the deletion.
5. THE Portal SHALL display all Doctor profiles in a searchable list with their name, specialization, and availability status.
6. THE Portal SHALL allow a Profile Image upload for each Doctor, stored in Firebase Storage, with a maximum file size of 5 MB and formats restricted to JPG and PNG.

---

### Requirement 11: Analytics and Reporting

**User Story:** As an Admin, I want to view detailed analytics on patient volume, revenue, and visit trends, so that I can make data-driven decisions about clinic operations.

#### Acceptance Criteria

1. THE Analytics_Module SHALL display total patient registrations grouped by month for a user-selectable date range.
2. THE Analytics_Module SHALL display total revenue (sum of Treatment Charge) grouped by month for a user-selectable date range.
3. THE Analytics_Module SHALL display patient counts broken down by Visit_Type for a user-selectable date range.
4. THE Analytics_Module SHALL display a list of the top 5 most active doctors ranked by number of patients treated in the selected date range.
5. THE Portal SHALL provide a Daily Report view showing all Patient_Records created on a selected date.
6. THE Portal SHALL allow the Admin to export any analytics view as a PDF or Excel file.
7. WHEN the Analytics_Module is loaded, THE Portal SHALL render all charts within 5 seconds for datasets up to 10,000 records.

---

### Requirement 12: Camp Management

**User Story:** As an Admin, I want to create and manage free dental camp events and associate patient records with specific camps, so that camp outcomes can be tracked and reported separately.

#### Acceptance Criteria

1. THE Portal SHALL allow an Admin to create a Camp event with the following fields: Camp Name, Location, Date, Organiser, and Notes.
2. WHEN a Camp event is created, THE Portal SHALL store the record in the `appointments` Firestore collection with a unique Camp_ID.
3. WHEN a Free Camp Patient_Record is created while a Camp event is active, THE Portal SHALL associate the Patient_Record with the Camp_ID.
4. THE Portal SHALL display a Camp summary view showing the total number of patients, doctors present, and treatments performed for each Camp event.
5. THE Portal SHALL allow the Admin to export a Camp report as a PDF containing all associated Patient_Records.

---

### Requirement 13: Multi-Role User Management

**User Story:** As an Admin, I want to create and manage user accounts with different roles, so that clinic staff have access only to the features appropriate for their responsibilities.

#### Acceptance Criteria

1. THE Portal SHALL support three user roles: `super_admin`, `receptionist`, and `doctor`.
2. WHEN an Admin creates a new user account, THE Portal SHALL store the user's email, role, and `createdAt` timestamp in the `admins` Firestore collection.
3. THE Portal SHALL restrict delete operations on Patient_Records and Doctor profiles to users with the `super_admin` role.
4. THE Portal SHALL restrict the Settings and User Management pages to users with the `super_admin` role.
5. WHEN a `doctor` role user logs in, THE Portal SHALL display only the patients assigned to that doctor.
6. THE Portal SHALL allow an Admin to deactivate a user account, preventing login without deleting the account record.

---

### Requirement 14: Notifications and Reminders

**User Story:** As an Admin or Receptionist, I want the Portal to send follow-up reminders to patients, so that patients do not miss their scheduled appointments.

#### Acceptance Criteria

1. WHEN a Patient_Record has a Follow-Up Date set, THE Portal SHALL display a notification in the Dashboard on the day of the follow-up.
2. THE Portal SHALL display a notification badge count on the notification icon in the top navigation bar reflecting the number of follow-ups due today.
3. WHERE the WhatsApp Reminder feature is enabled in Settings, THE Portal SHALL trigger a WhatsApp message to the patient's Mobile Number on the day of the follow-up.
4. WHERE the SMS Reminder feature is enabled in Settings, THE Portal SHALL trigger an SMS to the patient's Mobile Number on the day of the follow-up.
5. THE Portal SHALL provide an Appointment Calendar view displaying all follow-up dates as calendar events.

---

### Requirement 15: Firebase Security and Data Integrity

**User Story:** As an Admin, I want all data to be stored securely in Firebase with role-based access rules, so that patient data is protected from unauthorised access or modification.

#### Acceptance Criteria

1. THE Firestore SHALL enforce security rules that deny all read and write access to unauthenticated requests.
2. THE Firestore SHALL enforce security rules that restrict delete operations on the `patients` and `doctors` collections to users whose `admins` document has `role == "super_admin"`.
3. THE Storage SHALL enforce security rules that allow file uploads only from authenticated users and restrict file downloads to authenticated users.
4. THE Storage SHALL enforce file type validation at the security rule level, rejecting uploads of file types other than PDF, JPG, PNG, and DOCX.
5. THE Portal SHALL record every create, update, and delete operation in the Activity_Log collection with the actor's UID, the affected document ID, the operation type, and the UTC timestamp.
6. THE Firestore SHALL enforce security rules that prevent a `doctor` role user from reading Patient_Records not assigned to them.

---

### Requirement 16: UI, Accessibility, and Responsiveness

**User Story:** As a clinic staff member, I want the Portal to be usable on both desktop and mobile devices with a professional medical aesthetic, so that I can manage patients from any device.

#### Acceptance Criteria

1. THE Portal SHALL render correctly and be fully functional on screen widths from 375px (mobile) to 1920px (desktop) without horizontal scrolling.
2. THE Portal SHALL apply a white and light-blue medical professional colour theme with blue accent elements consistently across all pages.
3. THE Portal SHALL use Framer Motion animations for page transitions and modal appearances with a duration not exceeding 300ms to avoid perceived slowness.
4. THE Portal SHALL support a Dark Mode toggle in Settings that persists the user's preference across sessions using localStorage.
5. THE Sidebar SHALL collapse to an icon-only rail on screen widths below 768px and expand on user interaction.
6. THE Portal SHALL meet WCAG 2.1 Level AA colour contrast requirements for all text and interactive elements.
7. THE Portal SHALL display a loading skeleton or spinner for all data-fetching operations lasting more than 500ms.

---

### Requirement 17: Settings and Configuration

**User Story:** As an Admin, I want a Settings page to configure clinic details, notification preferences, and system options, so that the Portal reflects the clinic's specific operational setup.

#### Acceptance Criteria

1. THE Settings page SHALL allow an Admin to update clinic details including: Clinic Name, Address, Contact Number, and Logo.
2. THE Settings page SHALL allow an Admin to enable or disable WhatsApp Reminders and SMS Reminders independently.
3. THE Settings page SHALL allow an Admin to configure the default page size for patient tables (10, 25, or 50).
4. WHEN an Admin saves Settings changes, THE Portal SHALL persist the updated values to the `settings` Firestore collection within 5 seconds.
5. THE Settings page SHALL provide a Data Backup option that exports all Firestore collections as a JSON file downloadable by the Admin.

---

### Requirement 18: Activity Logs and Audit Trail

**User Story:** As an Admin, I want to view a complete audit trail of all actions performed in the Portal, so that I can investigate any data changes or access issues.

#### Acceptance Criteria

1. THE Activity_Log SHALL record every Patient_Record create, update, and delete event with: actor UID, actor role, affected Patient_ID, operation type, changed fields, and UTC timestamp.
2. THE Activity_Log SHALL record every Doctor profile create, update, and delete event with the same fields as criterion 1.
3. THE Portal SHALL display the Activity_Log as a paginated, filterable table on the Admin-only Audit Trail page.
4. THE Activity_Log SHALL be append-only; THE Firestore security rules SHALL deny update and delete operations on the `activity_logs` collection for all roles including `super_admin`.
5. WHEN the Audit Trail page is loaded, THE Portal SHALL display the 50 most recent log entries by default, sorted by timestamp descending.
